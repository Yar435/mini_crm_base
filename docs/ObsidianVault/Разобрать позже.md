# Prod-like через Docker Compose

Зачем: проверить, что всё взлетает **как в CI/проде** (gunicorn, Postgres, Redis, Celery).

## 2.1 Подготовка .env

Создай/обнови `.env` в корне **под Docker** (значения без секретов примерные):

`DJANGO_SECRET_KEY=dev-key-for-docker ALLOWED_HOSTS=127.0.0.1,localhost DATABASE_URL=postgresql://app:app@db:5432/app REDIS_URL=redis://redis:6379/1  CELERY_BROKER_URL=redis://redis:6379/1 CELERY_RESULT_BACKEND=redis://redis:6379/1  # Если будешь юзать prod.py: # CSRF_TRUSTED_ORIGINS=http://127.0.0.1,http://localhost`

**Почему так:** Docker-compose уже поднимает `db` и `redis` с этими именами; `web/worker/beat` ожидают их по этим URL.

## 2.2 Сборка и подъём

`# Сборка prod-образа из Dockerfile (multi-stage) docker compose build  # Подъём всех сервисов docker compose up -d  # Проверяем статусы docker compose ps`

Ожидаешь как у тебя:

`web      Started worker   Started beat     Started flower   Started (порт 5555) redis    Started db       Healthy`

**Почему так:** мы убеждаемся, что сервисы живы и зависимости прогреты.

## 2.3 Смоук-проверки

`# health curl -i http://127.0.0.1:8000/health/  # Swagger # открой в браузере http://127.0.0.1:8000/api/docs/  # Celery beat/worker docker compose logs -f worker | sed -n '1,120p'      # должны быть принятые таски (heartbeat) docker compose logs -f beat   | sed -n '1,120p'  # Flower UI # http://127.0.0.1:5555  (на проде не забудь повесить basic_auth)`

**Почему так:** `/health/` — базовый индикатор; логи worker/beat покажут, что очередь живая; Swagger — что схема валидна и авторизация работает.
